# 分析以下代码的单元测试需求，并输出测试分析报告

你正在为当前仓库编写测试分析，不要直接修改代码，也不要默认输出完整测试脚本。你的任务是基于指定目标产出一份**中文测试分析报告**，帮助后续模型或工程师编写高质量单元测试。

## 项目约束

1. 这是一个 **NestJS + TypeScript** 项目。
2. 测试框架是 **Jest + ts-jest**。
3. 单元测试文件应与被测文件放在同目录，使用 `*.spec.ts` 后缀。
4. 端到端测试放在 `test/*.e2e-spec.ts`，本命令以单元测试分析为主。
5. NestJS 单测优先使用 `@nestjs/testing`。
6. 请求校验相关逻辑要关注 `class-validator` 与 `ValidationPipe`。
7. 输出必须严格贴合仓库现有代码，禁止虚构不存在的 API、类型、依赖、路径或模块。

## 分析目标

请针对以下目标进行分析：

$ARGUMENTS

## 分析要求

请优先识别并覆盖以下内容：

1. **待测功能点与业务分支**
   - 对外暴露的方法、路由、返回值
   - 关键条件分支
   - 依赖调用关系（如 controller 到 service）

2. **Happy Path**
   - 正常输入下的预期行为
   - 成功返回的数据结构、状态码或副作用

3. **边界值与异常路径**
   - `null`、`undefined`、空字符串、空数组、零值、负数
   - 非法参数、越界访问、找不到资源
   - 预期异常（如 `NotFoundException`）
   - 输入转换和校验失败场景（如 `ParseIntPipe`、DTO 校验）

4. **Mock / Fixture / Test Module 建议**
   - 哪些依赖需要 mock
   - 是否建议使用 `TestingModule`
   - 是否需要固定测试数据或工厂函数

5. **测试文件建议**
   - 推荐测试文件路径
   - 建议的 `describe` 结构
   - 建议覆盖的 `it` 用例标题

6. **风险与未覆盖项**
   - 当前代码中难以稳定测试的部分
   - 需要额外上下文、依赖或集成测试才能覆盖的内容
   - 建议优先级

## 特殊关注

如果目标包含以下类型文件，请附加对应分析：

- **Service**：方法输入输出、状态变更、异常分支、集合增删改查、副作用
- **Controller**：路由映射、参数解析、Pipe/DTO 校验、HTTP 状态码、异常传播、service 调用
- **DTO**：字段必填/可选、类型限制、邮箱/字符串等校验规则
- **Module**：通常不作为单测重点，除非存在动态模块或复杂 provider 装配

如果目标是目录，请按文件逐个给出测试建议，并指出优先覆盖顺序。

## 输出格式

请严格按以下结构输出：

### 1. 测试概览
- 目标文件或目录
- 建议优先级
- 推荐测试类型（service / controller / dto）

### 2. 待测点清单
- 按方法、路由或类职责列出待测点

### 3. 建议测试场景
- Happy Path
- 边界值
- 异常路径
- 校验相关场景

### 4. Mock 与测试组织建议
- 需要 mock 的依赖
- 推荐测试文件路径
- 推荐的 `describe` / `it` 组织方式

### 5. 风险与缺口
- 当前难点
- 未覆盖项
- 需要额外上下文的地方

### 6. 专业测试脚本生成 Prompt

在报告最后，输出一段可直接复制给模型的 Prompt，要求如下：

- 以“请为以下 NestJS/TypeScript 代码编写 Jest 单元测试”开头
- 明确要求输出完整、可运行的测试文件
- 明确要求测试文件放在与被测文件同目录，文件名使用 `.spec.ts`
- 明确要求覆盖正常路径、边界场景、异常分支、错误处理
- 明确要求严格使用现有接口和返回值，不得伪造 API 或类型
- 明确要求优先使用 `@nestjs/testing` 组织 NestJS 单测
- 明确要求信息不足时先列出缺失依赖、mock 假设与待确认点
- 将当前分析报告中提炼出的关键测试点、异常类型、mock 建议、推荐文件路径一并写入 Prompt

## 质量要求

输出必须满足以下标准：

- 结论具体，不写空泛建议
- 测试点要能直接转成 Jest 用例
- 与当前仓库技术栈一致
- 重点覆盖真实逻辑风险，而不是机械罗列
- 如果发现现有代码本身存在影响测试设计的问题，可单独指出
